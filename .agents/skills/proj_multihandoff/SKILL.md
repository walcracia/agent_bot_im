# 项目多 Agent 接续

源码、设计决策、验证证据和下一步工作以 Git 中的文件为交接依据。聊天摘要、本机绝对路径及父目录独有文件不能成为下一位 Agent 的必要依赖。技能名称按用户要求保留为 `proj_multihandoff`。

## 首次接手与后续同步

- **首次必须提供 Git 地址。** 用户消息或既有任务上下文都可作为输入；没有地址且目标不是已有仓库时，询问地址，不猜测仓库。先检查目标父目录、相邻项目的 `AGENTS.md` 和布局说明，再决定项目目录。相邻项目只是布局参考，不能套用其业务规则，也不要修改它们。
- 检查目标是否为空、是否位于其他 Git 仓库内。首次将仓库克隆到明确的项目根目录，避免产生意外的 `项目/仓库/仓库` 嵌套；保留远端自身布局。目标已有文件时先确认归属，不能覆盖或把它们自动清空。
- **非首次从当前仓库配置恢复地址。** 先确认 Git 根目录、当前分支、upstream、origin、worktree 和未提交修改；用户另给地址时须与 origin 核对，不自动改 remote。
- 干净工作区执行 `git fetch --prune origin`，确认分支关系后 `git pull --ff-only`。脏工作区保留现状，可先 fetch 并审查远端；不要自动 stash、reset、clean 或覆盖文件。detached HEAD、无 upstream、无提交、远端不符或分叉时明确说明并处理具体问题，不能假装已同步。
- 网络、认证或权限失败时保留本地内容和失败记录；不能把旧代码称为最新代码。提交前后都检查其他 Agent 是否改变了工作区。

可使用附带的 [同步脚本](scripts/sync_project.py) 处理普通 origin 仓库（Python 3.9+、本机 Git，无第三方库）。脚本不提交、不推送、不配置凭证；脏树和异常状态会拒绝自动同步。仓库未使用 origin 或需处理分叉时，按上述原则人工检查。

```text
# 首次：明确目标项目根；地址不要包含令牌或密码
python <技能目录>/scripts/sync_project.py --project <项目根> --git-url https://github.com/owner/repo.git
# 后续：在项目根直接执行，无须再次提供地址
python <技能目录>/scripts/sync_project.py
# 或指定已有项目根
python <技能目录>/scripts/sync_project.py --project <项目根>
```

## 恢复上下文与目录

进入、重启、交接或上下文压缩后，重新读取仓库 `AGENTS.md`，以及已有的 `RESTORE.md`、`environment/state.json`、`workspace/docs/HANDOFF.md` 或等效文件，再按任务读取设计和最新过程记录。分支、提交、发布、服务运行情况以当前实查为准；旧日志中的路径、客户端已打开、已登录、测试通过只代表当时环境。

已有项目保留约定和源码位置。没有现成结构的新项目，默认按需要采用：

```text
项目根/                .git、AGENTS.md、README.md、RESTORE.md
  workspace/           源码及 docs/ 中的设计、接口、决策、过程、测试、交接
  references/          可共享的参考资料
  outputs/             适合交付的脱敏报告或小型产物
  environment/         示例配置、恢复脚本、状态；真实配置和数据必须忽略
    config/ scripts/ logs/ verification/
```

目录按实际需要创建，不为占位制造空目录。只存在父目录的必要布局规则应在本仓库保存可共享副本，并改为可解析的相对链接。发布大包用项目已有的 Release/制品渠道，不能把运行环境和整套依赖塞进 Git。

## 开发与验证

1. 先在仓库文档写清本轮范围、设计选择与可观察的验收标准，再实现。保持最小必要变更，延续原有技术栈；未获具体任务时完成接续准备，不擅自扩展功能。
2. 使用项目独立的依赖、配置和测试数据。脚本以自身位置定位项目根，避免写死某台机器路径。不能启动冲突端口、使用正式数据库做测试或改变其他项目的运行环境。
3. 多 Agent 并行时分配清楚的文件或模块责任；不要让多个 Agent 同时写同一文件。共享工作区先检查现有变更，不用“恢复干净”删除同伴工作。集成人负责审查 diff、运行整体验证并交付。
4. 运行与变更相称的真实验证，记录命令、环境、结果和未执行项。区分历史验收、本机本轮验证、模拟验证与真实集成；失败、未执行、部分通过分别记录，不刷重试掩盖失败。
5. 将阶段变化和实质决策写入已有的设计/过程/测试文档，更新交接入口。记录尚缺信息和下一步，不复制密码、聊天正文、附件或原始日志。

交接至少让下一位 Agent 找到：当前目标与范围、实际分支/提交、主要改动、验证命令及结果、限制或失败、环境恢复方式、下一步，以及远端交付状态。提交自身 SHA 可由 Git 查询，避免为回填自身哈希无限追加提交。

涉及后台长任务、多会话或外部Agent执行时，再读 [长任务与并发接续](references/long-running-work.md)。普通小改动无需引入调度、监督或多进程架构。

## Git 交付

- 是否推送取决于**该项目的用户会话授权或仓库约定**。本技能不授予其他项目永久发布权限。已有授权时直接完成必要交付；未授权时先准备可审查结果，再按实际需要取得授权。
- 审查 `git status`、diff 和 `.gitignore`。真实凭证、`.env`、聊天/附件、数据库、用户目录、原始日志、虚拟环境、依赖缓存不入库。分享示例配置、锁定依赖和脱敏报告；发现秘密不直接打印内容。
- 按本轮明确文件清单 `git add -- <文件...>`，再审查 staged diff；不能盲目 `git add .` 或混入其他 Agent/用户未交付的修改。不要擅改全局 Git 身份。
- 按项目版本约定执行本地 commit；要求迭代标签时创建新的 annotated tag。不要 force push、移动已发布 tag 或重写他人历史。普通工作不额外创建 Release；项目约定需要时再发布。
- 推送明确的分支/新标签。远端抢先更新造成拒绝时先 fetch 审查，保留双方工作，按具体情况整合并重验；不能用强推解决。
- 推送后用 `git ls-remote` 或服务端 API 核对分支 SHA 与 `git rev-parse HEAD`；annotated tag 同时核对 tag 对象及 peeled commit。区分“本地已提交”“推送失败/待推送”“远端已确认”，只在实查后称已上传。最后检查工作区并向用户报告提交、分支、验证及剩余事项。

## 分发本技能

整个 `proj_multihandoff/` 文件夹可独立复制到目标 Agent 的技能目录，入口为 `SKILL.md`；不依赖创建者机器的其他技能。用户要求单独托管时，在项目父目录的技能集合目录保留可上传副本；由用户给出的仓库和授权决定是否上传该副本。项目需要靠 Git 自行接续时，也可将同一包放入仓库约定的技能目录，并记录副本同步方式，避免多个版本无主漂移。
